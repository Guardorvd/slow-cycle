## 4. Полная inventory methodology

1. Повторить branch/HEAD/porcelain/staged/unstaged/untracked фиксацию; при изменении source identity относительно плана сверить delta и applicability, при существенном изменении переутвердить amendment. Снять hashes защищённых файлов; чужие dirty paths не изменять/не присваивать.
2. Сопоставить `git ls-files scripts/test`, `rg --files --hidden scripts/test` и filesystem listing. Accounting включает .gd/.uid/instructions, ignored/untracked findings с происхождением; не считать их автоматически current tracked suites. Затем repo-wide discovery по entrypoint/call content, включая `scripts/`, scenes/resources, project autoloads/input/render settings, README/TEST_PLAN/docs/history/reports, shell/CI launch references. Не ограничиваться `test_*` и не доверять утверждению «all suites».
3. Прочитать **каждый файл полностью**, включая helpers/генераторы и embedded cases. 4. Построить два графа ссылок: executable calls (runner→child/helper/scene/production owner) и documented invocation (commands/gates/manual use). Отделить OS.execute git от запуска тестов. Для master раскрыть каждый child tier, собственные in-engine группы и propagation errors; проверить cwd/--path/--script, output capture, timeout, hangs/abort и cleanup. 5. Выделить subrows в mixed suites по owner/типу проверки/evidence/authority. 7. Любой injected stub фиксируется: boundary и production logic, которое он заменяет; не объявлять такой путь полной terrain integration.

9. Duplicate candidate требует одинаковых requirement, real call path, oracle, inputs и evidence scope; shared helper или два масштаба coverage сами по себе не duplicate. Orphan candidate требует отсутствия executable **и** documented/manual/gate consumers с записью точного search scope; отсутствие в master недостаточно. Всё остаётся на диске.

Все unknown/conflicts имеют owner и следующий human decision, без замалчивания. Необнаруженный external tool не выдумывать.

## 5. Предлагаемая schema `docs/TEST_MATRIX.md`

Формат — Markdown: компактный file index + детальные group records, authority/running policy, conflict ledger и evidence limitations. Большая горизонтальная таблица не должна скрывать prerequisites/actual predicates.

| Поле record | Обязательное содержание |
|---|---|
| Identity | Stable row ID, canonical path, parent/group/entrypoint, source SHA256, audit HEAD/date; source line/function anchors |
| Role | `runner`, `helper`, `capture`, `audit`, `fixture`; secondary roles и consumers; assertion oracle есть/нет; subprocess/standalone/scene-only |
| Contract / owner | Конкретное проверяемое свойство, real production owner/call, inputs/outputs/failure conditions; product/governance reference; stable invariant vs implementation-specific expectation |
| Authority | Одна из пяти approved categories для homogeneous check row; rationale, candidate/approved decision state, human approval reference/digest/date; mixed parent с child IDs, без фиктивной шестой категории |
| Evidence capability | Явный набор способных доказать E-levels по группам, prerequisites для каждого и исключённые claims; никаких автоматических max-level inheritance |
| Prerequisites / command | Точная существующая команда/cwd/entrypoint, Godot version/build/assert enabled, import/class cache, headless/display/Vulkan, scene/input/collision layers, seed/config before ready/CLI override, output permissions/files/manifest/source match |
| Coverage | Expected **и доступная measured** completion: seeds/derived seeds/route choices/arms/ranges/chunks/events/frames/time/points/contact counts; real/proxy/teleport/synthetic/geometry-replay labels; неисполненные branches |
| Oracle / reporting | Actual predicates/thresholds/units, printed vs asserted, reason specificity, assertion counting mechanism, completion marker, failure/exit propagation, internal/external timeout/cleanup/log handling |
| Limits / blind spots | Empty coverage, fallback/stubs/order/pruning gaps, spatial/seed bounds, renderer/physics/performance/human exclusions; source-backed defect vs unverified suspicion |
| Required-for / blocking | Existing mandatory source, change→consumer trigger, proposed supplemental trigger, blocking scope and conflict conditions; approved vs proposed policy, без gate weakening |
| Evidence status | Static-audit completeness; current runtime `NOT_RUN`; separately dated last report result+revision/diff/source identity+seed/artifact availability; missing/unknown не PASS |
| Relations | invokes/used-by, overlaps/duplicate candidate/orphan candidate с evidence; current legacy consumer и future migration boundary |
| Conflict / review | Conflict IDs, unresolved requirements/budget/oracle mismatches, owner/action/approval, independent reviewer resolution |

Helper/fixture без самостоятельного oracle получает role/consumers/prerequisites, **не вымышленную suite category или PASS**: authority field «не самостоятельная проверка», ссылки на реальные check rows. Если helper содержит отдельный проверяемый контракт, описать его тестирующий consumer; если это embedded check — child record. Role orthogonal authority: observational audit может содержать blocking integrity assertions; capture tool может иметь artifact guards; runner может вызывать historical checks. Category enum не расширяется.

Source fact, evidence capability и actual run result — три отдельных поля. Наличие E4/E5-capable path не означает свежий E4/E5 PASS. У каждого report нужно указать и runner source identity, и production/config identity; различие capture/logger source sets обязательно сохраняется.

## 6. Правила будущего назначения пяти категорий

Применять после полного trace на homogeneous check group, не по age/name/location/PASS. В этом плане никаким существующим suite/group категории не присвоены.

| Категория | Решающее основание | Failure/migration boundary |
|---|---|---|
| ACTIVE_CONTRACT | Explicit current requirement конкретного контракта, owner и реальный чувствительный oracle; target applicability подтверждена authority source | Падение блокирует задачу в указанном контрактном scope; assertion mutation только по отдельному specific approval |
| REGRESSION_GUARD | Защищает реализованную работающую систему и её consumers от accidental regression; coverage/limitations известны | Блокирует, когда owner в scope или мог быть затронут, включая indirect consumers; объяснить dependencies |
| LEGACY_CONTRACT | Проверяет конкретное архитектурное поведение/representation, которое approved target сознательно заменяет; указан старый owner, phase и exact conflict | Текущий legacy runtime продолжает защищаться; конфликт не заставляет новый owner принимать старый invariant. Падение legacy consumer нельзя игнорировать; migration resolution требует evidence и человеческого решения |
| OBSERVATIONAL | Метрика/statistics/coverage measurement без согласованного acceptance budget для этого scope | Число само по себе не блокирует. Existing asserted budget/gate не становится optional от этого label: отдельное approval требуется для любого изменения обязательства; integrity/completion failures указываются отдельно |
| HISTORICAL | Доказано, что проверка сохраняет завершённую sprint-specific history и не защищает текущий requirement/consumer/gate; есть конкретное human решение | Не входит автоматически в новый acceptance; category не удаляет файл и не отключает существующий mandatory source |

Порядок: определить requirement+owner+oracle → проверить surviving invariant/current consumers → выявить approved architecture conflict → проверить budget authority → проверить историческое назначение/все consumers → предложить обоснованную category. Для смешанного файла нужны subrows; нельзя объединить устойчивую математику с DAG/zero-post/source-text checks под одним удобным label.

Unknown budget/owner/oracle/consumer = pending decision с причиной, не автоматический OBSERVATIONAL/HISTORICAL. Слабый тест может защищать важный contract: отдельно фиксировать intended protection и actual proof gap, не повышать доказательность. Orphan/duplicate статус не определяет category и не разрешает retirement.

| Уровень по Test Strategy | Требование к доказательству и audit rule |
|---|---|
| E0 Parse | Реальный engine parse/start без parse errors в заявленном scope; source inspection/Markdown проверка не E0; build/import prerequisites указаны |
| E1 Pure Domain | Real math/data logic + oracle; локально переписанная формула или source substring не доказывает production behavior, RefCounted label не доказательство purity |

| E3 Runtime | Main/production-equivalent scene и действительная materialization/commit/lifecycle, actual effective config; handcrafted equivalent fixture требует justification; телепорт допустим лишь для заявленного runtime observation |
| E4 Physics | Registered collision и реальный BicycleController/Input-driven interaction в заявленной группе; отдельный ray/collider факт описывается как collision evidence, не сертифицирует поездку. Initial placement допустим для локального episode, per-frame pose forcing не continuous ride |
| E5 Vulkan Visual | Реальный Vulkan renderer/driver/version, saved+reloaded PNG, pose/scene/seed/source context, фактический просмотр. Flat fixture/camera image не доказывает весь procedural world или beauty acceptance |

Q0 фиксирует существующие обязательства и предлагает traceable supplemental triggers; **не вводит и не отменяет mandatory gates**. В каждой записи различить «сейчас обязан по source», «предлагается для конкретного future scope», «не подтверждает данный acceptance».

Их текущие blind spots не разрешают skip или замену real rider телепортом. Docs-only Q0 не является generation change; данные gates не запускаются для доказательства Markdown diff и не waived для следующей feature.

Будущая trigger map строится от actual owners: path/math/validators→contract/seam/determinism groups; grammar/events→event/intent/rhythm; graph/branch→DAG/FSM/site/pacing/stream integration; terrain/surface/foliage→topology/contact/clearance/verge/committed collision; player/Input/recovery→нужные lab/physics/core/UI consumers; camera/render/materials→relevant captures; logger/session→manifest/provenance/replay/I/O guards; streaming/lifecycle→bounded runtime/soak/memory checks. Exact existing entrypoints и ограничения заносятся по факту полного аудита, без нового runner.

При migration проверять затронутые old и new consumers раздельно. Новый RegionRouteGraph не обязан быть DAG, но regression старого RoadGraph остаётся проблемой до approved retirement/adapter gate. Numeric/statistical observation без approved budget не новый blocker; asserted или governance-mandatory budget не снять документальным label. Необъяснённое падение current gate/недостающее обязательное evidence блокирует completion affected task; исторический failure нельзя переименовать ради зелёного статуса.

## 9. Conflict-resolution process и approval checkpoints

Conflict record: ID; row/group/source function+lines+hash; current expected/asserted/actual path; защищаемый owner/consumer; Blueprint/Master requirement/phase; current mandatory obligation; available evidence и unknowns; stable invariant отдельно от legacy representation; влияние failure на current runtime/new migration; documentary proposal; human owner и decision reference.

1. Сохранить tests/gates/production; записать точный конфликт и не пытаться починить его.
2. Проверить, что расхождение относится к архитектурному ожиданию, недостаточному oracle/evidence, stale threshold/comment или фактической regression. Не выбирать target/code authority по удобству.
3. Предложить specific документальный category/limitation/blocking-scope decision; reviewer проверяет surviving invariant/consumers/mandatory sources. Test mutation/threshold change/repair уходит в **другую отдельно approved задачу**.
4. До решения человека conflicting assignment остаётся candidate/pending и не влияет на выполнение gates. При противоречии frozen/tool-applied rule остановить только затронутую decision, явно эскалировать; unaffected audit можно продолжать.
5. После explicit approval записать exact row IDs/content digest/условия. Устные/текстовые решения valid по D1, но approval общего Q0-аудита не является разрешением исправлять tests или выключать gates.

Два review checkpoint будущего исполнения:

- **A — approval этого ExecPlan/version/scope** разрешает полный статический аудит и draft documentary map с candidate rows. Сейчас STOP перед A.
- **B — человеческое review конкретной map/digest и category/conflict decisions** разрешает сделать эти назначения accepted. Draft TEST_MATRIX имеет статус PROPOSED; до B ни одна candidate assignment не является действующей reclassification. Любое gate/mutation expansion требует отдельного amendment и не входит в B по умолчанию.

Если B отклонён/частичен, сохранить draft и pending conflicts, не объявлять Q0 COMPLETE. Не добавлять в matrix «исправленные» требования новой architecture; не переносить тривиальные source-string checks в вечные product contracts.
