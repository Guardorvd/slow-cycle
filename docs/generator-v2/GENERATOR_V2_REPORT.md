## 2. Новые замеры этой ревизии

Все замеры — без bake: Godot 4.7.2 standard (без C#-ядра) в Linux-контейнере, R0–R3 и один проход R5 (раунд 0, без R6/R7). Скрипты: [slope_probe.gd](slope_probe.gd) (r1), [access_probe.gd](access_probe.gd) (r2). Время — за один прогон, повторов нет.

### 2.1 Уклоны (замер r1, без изменений)

Склоны 23–60 % занимают 21–31 % суши, перепады крупных склонов 300–585 м (184729, 3628391, 2024). Вывод r1 о «закрытой половине суши» исправлен выше (№9).

### 2.2 Доступ от дорог (новое)

Дороги — коридоры BACKBONE и SECONDARY раунда 0 R5 (не опубликованная сеть). «Пара спуска» — две точки дорог разных рёбер с перепадом ≥ 60 м на расстоянии 150–2000 м, прямая между ними без воды, ≥ 90 % точек с уклоном < 0.8 и средним уклоном ≥ 0.15.

> **Уточнение r2.1 (определения поиска).** «Уклон» в этом поиске — модуль градиента местности |∇h| в точке, на сетке 16 м естественной поверхности (до R7), а «средний уклон ≥ 0.15» — среднее |∇h| по точкам прямой между двумя точками дорог. Это **не** уклон между концами: у лучшей пары 3628391 перепад 107 м на 1.9 км, то есть 5.6 % между концами, при среднем |∇h| вдоль прямой 0.32. Точки дорог — каждая 3-я станция коридоров BACKBONE и SECONDARY, а пары составлялись из каждой 3-й из них (каждая 9-я станция); SINGLETRACK и TECHNICAL не участвовали. «0 пар на 184729» — результат именно этого поиска, а не доказательство, что спуска от дороги к дороге нет.

### 2.3 Разнообразие географии (чтение кода)

`macro_geography_generator.gd` строит **одну топологию** `MOUNTAIN_RIVER_VALLEY`:
- одна сквозная долина вдоль оси u (центральная или смещённая), полуширина дна всегда 70–150 м (`:103–110`);
- один главный хребет на одной стороне (сквозной, массив или двойной с перевалом) с 2–4 вершинами (`:124–147`);
- 3–6 отрогов к долине, на дальней стороне хребет, холмы или открытое плато, 1–2 полки на склонах, иногда верхняя котловина (`:153–247`).

Дискретная композиция — 2 × 3 × 3 × 3 = 54 варианта, плюс непрерывные параметры и 8 поворотов/отражений кадра (`:256`). Гидрология жёстко ждёт этот архетип (`hydrology_generator.gd:70`), главная река идёт по оси долины. Числа §2.1 по трём сидам близки (плоского 27–30 %, круче 35 % — 44–49 %): сиды различаются деталями, а не устройством. Широкой долины, ущелья, ветвления долин, котловины с выходом через перевал, плато с оврагами и нескольких хребтов нет.

Полезная находка для расширения: хребты в оценщике уже задаются **сетью отрезков с полем расстояния** (`macro_terrain_evaluator.gd:299`, `_ridges`) и пространственным индексом ячеек, а долина — **одной осью** (`_base`, `:269`). Генерализация долины до сети отрезков по той же схеме — главный рычаг топологического разнообразия (§3.1).

## 3. Обновлённая архитектура

Порядок зависимостей: **композиция местности → карта возможностей езды → дороги и доступ → линии троп → композиция изменений земли → публикация → сеть и возврат.** Каждый слой имеет одного владельца и чистый доменный результат; runtime только рендерит и сталкивает.

### 3.1 География (владелец: R1 `MacroGeographyGenerator` + `MacroTerrainEvaluator` + C#-ядро)

**Подход: расширить существующий структурный генератор, без симуляции эрозии.** Мир собирается из примитивов-графов:

- **сеть долин** — дерево полилиний (ствол и 0–3 притока), у каждой ветви своя ширина дна и профиль бортов, участки-ущелья; рельеф долины — гладкий минимум профилей по ветвям (как `_ridges`, только «вниз»);
- **сеть хребтов** — уже есть; разрешить несколько групп (параллельные хребты), седловины между ними становятся перевалами между долинами;
- **врезы** — отрицательные отрезки с V-профилем (овраги на плато, кулуары);
- **плато и котловины** — уровень с бровкой; котловина с выходом через перевал или ущелье (обобщение нынешней верхней котловины).

Топологию задаёт **шаблон композиции** — небольшой генератор графа элементов, а не новая ветка кода на каждый мир. Примеры шаблонов: широкая долина с округлыми горами; узкая долина с крутыми бортами и полками; разветвлённые долины; котловина с перевалом; плато с оврагами; несколько хребтов с седловинами. Шаблон выбирается сидом, параметры варьируются внутри него. Каталог не фиксирован: новый шаблон — данные и комбинация тех же примитивов.

Обязательные следствия, которые нельзя забыть:
- **C#-ядро** (`MacroTerrainKernel.cs`) повторяет оценщик бит в бит: каждый новый примитив пишется дважды, а тест паритета (`tools/dev/kernel_parity.gd`) расширяется. Иначе либо теряется ускорение, либо ломается детерминизм.
- **Гидрология**: главная река идёт по стволу сети долин, а не по оси u; остальное уже строится маршрутизацией стока (`drainage_routing.gd`) и годится для любой топологии. Котловины уже превращаются в озёра (шаг 3 генератора).
- **Входы и выходы региона**: у шаблона не меньше двух краевых ворот для магистрали (сейчас их даёт сквозная долина).
- **Якоря R5** (`route_anchor_finder.gd` читает `spurs`, `main_nodes`, `benches`, `basins`) — переход на граф элементов.
- **Стоимость**: число элементов растёт, поэтому индекс ячеек нужен для всех примитивов, а не только для хребтов.

### 3.2 Карта возможностей езды (новый владелец: `RideOpportunityMap`, чистый растр)

Строится **до дорог** из R1-графа и рельефа R2/R3 (растр 8–16 м, секунды; уточняется до 4 м в зоне тропы после публикации земли). Находит:
- **склоны для спусков**: связные грани со стабильной экспозицией, перепадом, шириной вдоль горизонтали, без обрывов и воды;
- **естественные полки и выполаживания** (места для траверсов и разворотов), носы отрогов;
- **перевалы и седловины** (из R1-графа, не из шума);
- **спокойные зоны**: дно, луга, лес с малым уклоном;
- **верхние и нижние зоны петель**: пары «верх грани — низ грани» и до чего от них можно добраться.

Результат — ранжированный список **возможностей** с причиной и оценкой характера. Карта не проектирует тропы и не делает каждый склон проезжим.

### 3.3 Дороги и доступ (владелец: R5 `RoutePlanner`, R6/R7 без изменений для дорог)

- R5/R6 строят только BACKBONE и SECONDARY (раунды singletrack/technical убираются, оценка раунда и подсказки — только по дорогам; `route_planner.gd:62–64`, `region_network_builder.gd:141`, `hints_from`).
- **Согласование доступа ограничено по стоимости.** Карта отдаёт R5 до K целей доступа (верх лучших граней, седловины) как якоря нового вида `RIDE_ACCESS` в уже существующий раунд вторичных дорог. R5 либо подключает цель, либо нет. **Повторного планирования мира ради доступа нет.** Цель, до которой дорога не дошла, остаётся кандидатом для тропы-подъёма от ближайшей дороги или уходит из списка. Бюджет K и порядок фиксированы данными, поэтому результат воспроизводим.

### 3.4 Линии троп (владелец: новый `TrailLineBuilder`; `TrailNetworkPlanner` V1 замораживается)

Возможность → **замысел** (характер из §7) → **линия**. Для серпантина способ выбран в §4: конструктивная раскладка витков по грани + короткий поиск с курсом между якорями + геометрия из примитивов. Для спокойных троп (лес, луг) — тот же короткий поиск по коридору с курсом, без шпилек. Линия хранится как последовательность геометрических элементов (отрезок, дуга, переходная кривая), а не как свободные контрольные точки Catmull-Rom. Сэмплинг 1 м для проверки остаётся.

### 3.5 Композиция изменений земли (владелец: `TrailRealization` V2 → операции; `FinalSurface` их вычисляет)

Единое правило, заменяющее «ближайшую тропу» в `trail_displacement`:

1. **Каждая операция самостоятельна**: полка, поворот, подход к броду, пересечение дороги. У неё свой след (многоугольник), своя параметризация по **своему** участку линии (без поиска ближайшего отрезка по всем тропам), целевая высота T(x) и вес w(x) ∈ [0, 1], непрерывные внутри следа: w = 1 в ядре (полотно), плавно до 0 к краю (откосы).
2. **Поворот — одна операция**, которая включает концы обоих примыкающих витков. Внутри неё нет выбора ветки, поэтому нет разрыва между близкими витками.
3. **Приоритеты** (по возрастанию): откосы/полки → площадки поворотов → полотно тропы. **Дорожное полотно и его откосы старше всех**: вес операций тропы там 0, пересечение дороги в уровень меняет только подход тропы. Вода и её отступ — вес 0, кроме операции брода, которая меняет только подходы и не трогает русло.
4. **Сложение детерминировано**: h = h_base; для операций по возрастанию приоритета (при равенстве — по id): h ← lerp(h, T_i, w_i). Непрерывные T и w дают непрерывную поверхность, старший приоритет применяется последним.
5. **Конфликт ядер** (два полотна с разными целевыми высотами перекрываются) — это ошибка раскладки, а не повод усреднять. Витки раздвигаются локальной перераскладкой, иначе отказ с причиной.
6. **Откат**: операции принадлежат тропе; отказ тропы снимает её операции и пересобирает только тайлы её следа (§9).
7. **Локальная перепроверка** после сложения: полотно (уклон, боковой, ступень), непрерывность по краям следов (откосы не круче 1:1 выемка / 1:2 насыпь, как у дорог), затем финальная проверка на опубликованных треугольниках.
8. **Окружение**: деревья и камни исключаются по следу операции плюс отступ, а не только по ленте. Гидрология строится раньше и не пересчитывается; операции не заходят в русла (кроме подходов брода), поэтому сток не перекрывается. Визуально заметные выемки и насыпи помечаются для материала откоса.

## 4. Серпантин: сравнение способов для первого результата

Задача масштаба: 500 м перепада при 10 % по линии — около 5 км горизонтальной длины, то есть десятки витков на грани. Для первого чекпойнта реалистично 80–150 м перепада: 0.8–1.5 км линии, 2–6 поворотов. Узкая полоса вокруг кратчайшего пути такой серпантин исключает: витки уходят в ширину грани на сотни метров.

| Способ | Качество | Сложность | Стоимость | Главный риск |
|---|---|---|---|---|
| **A. Конструктивная раскладка**: выбрать грань; по перепаду и уклону витка посчитать число и длину витков; поставить развороты на естественные выполаживания у краёв грани (с допуском ±20–40 м); витки — траверсы с заданным уклоном и локальным обходом препятствий | Предсказуемая структура, явный контроль расстояния между витками, экономные развороты в удобных местах | Низкая–средняя: раскладка по горизонталям + 1D-подбор | Малая: сотни оценок высоты на виток | Сложные грани (врезы поперёк) и «правильный» однообразный вид — лечится нерегулярными разворотами по рельефу |
| **B. Поиск по состояниям курса с библиотекой манёвров** (решётка x, y, θ; дуги допустимого радиуса и примитив разворота) | Гибко на сложном рельефе, кривизна допустима по построению | Высокая: функция цены, тонкая настройка | Большая на длинных линиях; самопересечение и близость своих витков в A* не выражаются без зависимости от пути | Близкие витки и срезки; время в GDScript |
| **C. Комбинация (рекомендую)**: глобально — раскладка A (грань, витки, зоны разворотов); локально — короткий поиск B **между якорями** (виток 100–400 м, курс на концах задан); развороты — параметрические примитивы | Структура от A, обход препятствий от B, повороты гарантированы | Средняя | Ограниченная: поиск B короткий и с заданным курсом на концах | Нестыковка витка и разворота — решается тем, что разворот задаёт точку и курс входа/выхода |

**Минимальный вариант для первого чекпойнта — C**, причём B используется только для витков с препятствиями; прямой виток строится как траверс без поиска.

**Как не разрушить геометрию сглаживанием.** Линия собирается из элементов: прямые витки, развороты (дуга R с переходными участками длиной не меньше пути перекладки руля, §6) и сопряжения. Каждый элемент несёт свой радиус и коридор. Свободный Catmull-Rom через все точки не применяется. Допустимо только сглаживание внутри прямого витка с проверкой «не вышли из коридора, радиус ≥ допустимого». Итоговая проверка считает кривизну по фактическим отсчётам 1 м, а не по замыслу.

**Контроль близких витков.** Минимальный зазор между полотнами соседних витков = их следы плюс запас (не меньше суммы полуширин следов операций). Он закладывается раскладкой по горизонталям. Проверка после сборки: ни одна точка витка не ближе этого зазора к другому витку, кроме внутри общей операции разворота.

## 5. Развороты и изменение земли

Идеализированный плоский склон уклона s, разворот радиуса R по оси, полотно полуширины 0.65 м.

| Вид разворота | Формула максимального сдвига по оси | s = 0.25 | s = 0.40 | s = 0.60 |
|---|---|---|---|---|
| Плоская горизонтальная площадка R = 6 м | ≈ s·R | 1.5 м | **2.4 м** | **3.6 м** |
| Профилированный (винтовой) разворот R = 4.5 м, уклон по ходу 10 % | ≈ R·(s − 0.10·π/2) | 0.42 м | 1.09 м | 1.99 м |
| То же, уклон по ходу 15 % (TECHNICAL) | ≈ R·(s − 0.15·π/2) | 0.06 м | 0.74 м | 1.64 м |
| Профилированный R = 6 м, 10 % | ≈ R·(s − 0.157) | 0.56 м | 1.46 м | 2.66 м |

Плюс выравнивание полотна поперёк: ≈ s·0.65 м (0.16–0.39 м), плюс откосы: выемка 1:1, насыпь 1:2 расширяют след на |d| и 2|d| в каждую сторону. Вывод: **универсального предела 1–1.5 м нет.** Сдвиг определяют место (локальное выполаживание s ≈ 0.2–0.25 почти снимает земляные работы), вид поворота (винтовой против плоского) и радиус. Поэтому раскладка ставит развороты прежде всего на выполаживания и носы отрогов, а размер и положение площадки переменные.

Три разных исхода — разные причины в отчёте:
- **геометрически невозможно**: нет места для разворота и зазора витков на грани, обрыв, вода, дорога;
- **превышен рабочий бюджет**: сдвиг, объём или ширина следа выше бюджета операции (стартовые гипотезы, проверяются плейтестом): винтовой разворот |d| ≤ 1.5 м, полка |d| ≤ 0.6 м, след ≤ 14 м от оси;
- **нежелательный вид**: высота видимой выемки больше ~1.2 м или насыпь в лес — допустимо, но с пометкой материала откоса и штрафом в выборе.

## 6. Удобство манёвра, а не только радиус

Перепроверенные параметры (`bicycle_controller.gd`): руль 0.50 рад при v ≤ 0.83 м/с → 0.045 рад при 10.33 м/с, фильтр ввода 5 /с (постоянная времени ~0.2 с), слежение руля 12 /с, тормоз (export) 7.5 м/с², замер PR1: торможение 5.47 м/с², боковое 2.45 м/с², радиус 7.99 м при 8 м/с.

Профиль скорости по линии (прямой и обратный проход) учитывает:
- **скорость в повороте** v ≤ √(a·R), где a — комфортное боковое класса (стартовые гипотезы: спокойная тропа 1.8, TECHNICAL 2.45 м/с²). Для R = 4.5 м и 2.45 это 3.3 м/с;
- **торможение перед поворотом** с проектным замедлением (гипотеза 2.0 м/с²) с учётом уклона: на спуске 15 % гравитация добавляет около 1.6 м/с², которые тоже надо погасить. С 8 до 3.3 м/с нужно около 13 м чистого торможения;
- **видимость**: поворот должен быть виден не позже, чем за путь реакции (~1 с) плюс тормозной путь. До появления модели видимости берётся геометрическая прямая видимость по рельефу, растительность — позже;
- **перекладку руля** между противоположными поворотами: полный переход около 0.5–0.6 с, то есть ≥ 2–3 м прямой при 3–4 м/с;
- **ширину и запас ошибки**: для спокойных троп радиус берётся с запасом (скорость проектная ≤ 0.8 от предельной для радиуса), для сложных запас меньше, но поворот должен быть читаемым (виден вход и выход);
- **нижний предел скорости** не произвольный: на подъёме не ниже V_CLIMB 2 м/с (замер), спуск не требует почти полной остановки, если класс не TECHNICAL.

Установившийся радиус руля (§1 №10) — необходимое, но не достаточное условие. Решает **короткий Input-замер** существующим стендом `test_ride_envelope`: развороты R 4 / 4.5 / 5 / 6 м на ровном и на спуске 10–15 % с торможением со скорости витка, критерий — удержание полосы ±0.5 м без ручной подгонки. Физика велосипеда не меняется; если разворот R 4.5 неудобен, растёт R, а не меняется контроллер.

## 7. Характер и сложность

Сценарии (лесной flow, траверс, серпантинный спуск) — удобные имена, но выбор и оценка идут по **вектору характера** линии:

- уклон: средний, разброс, длительность устойчивых участков, короткие подъёмы внутри спуска (по таблице длины крутых участков PR1);
- скорость: средняя, максимальная, изменения (ускорение ↔ торможение), число и сила торможений на км;
- повороты: плотность, минимальный запас радиуса к скорости, развороты;
- ширина полотна, неровности (после появления мелкого рельефа), видимость вперёд;
- экспозиция: боковой обрыв вниз от полотна;
- ритм: длительность напряжённых участков и отрезков восстановления.

**Сложность = самый трудный обязательный элемент** (худший запас радиуса к скорости, самый крутой обязательный участок, самая узкая полоса над обрывом), плюс общая нагрузка. Средние значения сложность не определяют.

**Отбор сети учитывает, чего не хватает**: следующая тропа выбирается по расстоянию её вектора характера до уже выбранных (новизна) и по ценности места, а не только по собственной оценке. Синусы и одинаковые шпильки не являются источником разнообразия: развороты ставит рельеф, их шаг и радиус нерегулярны.

## 8. Возврат и реальные соединения

- **Сильная связность графа — минимум, но не удобство.** Для каждой тропы считается путь возврата от выхода к входу и к узлу дорог: длина, набор высоты, оценка времени по измеренному подъёму (устойчиво 5.6° по грубому грунту при 2 м/с), обязательная сложность. Тропа помечается, если возврат требует подъёма круче устойчивого предела без альтернативы, класса сложнее самой тропы или слишком долог по отношению к ней (порог — данные, стартовая гипотеза 3×).
- **Тупики не запрещаются**: путь к записанной цели (смотровая, берег, поляна) допустим, если обратный путь реально проезжаем, чаще всего та же тропа в обратную сторону с проверкой подъёма.
- **Пересечение на карте — не всегда соединение.** Соединение признаётся, если после публикации высоты полотен совпадают в допуске (стартовая гипотеза ±0.1 м), обе поверхности допускают движение и есть операция пересечения. Тропа под мостом или над тоннелем — не соединение (проверка зазора). Пересечение двух троп в уровень — развилка; в разных уровнях — нет.
- **Брод** оценивается по **финальному** дну и подходам после изменения земли: глубина по полотну (поверхность воды HydrologyPlan минус опубликованное дно), уклоны подходов по пределам тропы, ширина русла. Скорость течения не учитывается: в контроллере нет модели воды (§1 №16). Глубина 0.35 м — стартовый предел правдоподобия (ось колеса); его можно поднять для визуально мелкого широкого брода или снизить, если плейтест покажет, что «ехать по дну под водой» выглядит плохо.

## 9. Ускорение как часть архитектуры

### 9.1 Что известно и что нет

- Сопоставимо: только замеры одного кода, одной машины, одной сборки и одного числа потоков. Post-BC2 (63.4 с стадии троп, 7.4 с планировщик) и PERF_FIRST (61–64 с) — разный код, разбивки публикации нет ни в одном.
- Даже нулевая стоимость поиска даёт ≤ ~12 % стадии троп и ~3 % bake 246 с. Скорость V2 определяет **публикация** и её рост с числом и длиной троп, а также холодная генерация R5/R6 и тайлов.
- CPU-секунды, делённые на потоки, — не гарантированная экономия (длинный полюс, число раундов).

### 9.2 Архитектурные решения

- **Зависимости кэша по-настоящему**: земля (R0–R7 + тайлы) → дороги/доступ → **записи троп** (каждая с ключом своих входов: возможность, политика, земля в её зоне) → **публикация по тайлам** (ключ тайла = исходные массивы тайла + операции, пересекающие тайл, + вынужденные точки шва). Изменение одной тропы пересобирает её тайлы и соседей по шву, а не мир.
- **Пересборка затронутой компоненты**: тайлы, связанные общими следами операций и швами, собираются вместе. Вынужденные точки шва компоненты пересчитываются с нуля, чтобы результат не зависел от того, была ли сборка полной или частичной (проверка: дайджесты частичной и полной публикации совпадают).
- **Отказ одной тропы** снимает только её операции и пересобирает её компоненту; остальная сеть не перестраивается. Альтернатива публикуется так же.
- **Пространственные индексы**: операции по ячейкам; индекс треугольников опубликованной земли уже есть (`PUBLISHED_CELL_M`).
- **Пределы работы — счётчики, а не время**: раскрытия поиска, число кандидатов, проходы швов. Мир не зависит от скорости машины.
- **Инструмент одной тропы — два режима**: быстрый предварительный (линия, профиль скорости, операции на растре земли, карта сверху, секунды; **не** доказательство проезжаемости) и точный (публикация затронутых тайлов в dev-кэш, финальная проверка, запуск игры в точке тропы).

### 9.3 Возможности (приоритеты)

1. Разбивка времени стадии троп (подготовка растра, планирование, операции, уточнение, швы, финал, граф, повторные публикации) и рост с числом троп — **сначала замер** (GEN2-1).
2. Публикация по тайлам с кэшем и пересборкой компоненты — главный ожидаемый выигрыш при 10+ тропах (GEN2-3).
3. Удаление природных классов из R5/R6 — гарантированно меньше работы R6 на горных сидах; реальное время измеряется одним холодным bake (GEN2-3).
4. C#-порт короткого поиска — только если замер покажет, что он заметен.

## 10. Сохранение V1 (минимально достаточно)

Тег и переключатель **не гарантируют** воспроизводимости: ключ кэша включает версию движка и дайджест всего исходного замыкания вместе с `project.godot` (`region_bake_cache.gd:22–27`). Числа зависят от платформы (N-7: 2024 на Linux и Windows дал разные сети) и от сборки (стандартная против .NET с C#-ядром, хотя паритет ядра проверен). Поэтому V1 сохраняется **снимком результата**, а не поддержкой второго генератора:

1. **Код**: тег `generator-v1` на `d2ad73f` (локально; отправка по решению Директора).
2. **Продукты**: архив готовых кэшей `user://regions/<key>/` (manifest, network, тайлы, extras) для 184729, 3628391, 2024 с Linux-машины, а при возможности и с Windows-машины Директора. Плюс сводки bake (`tools/dev/bake_region.gd --out`) с дайджестами сети, тайлов и растительности.
3. **Конфигурация**: `trail_network.json` и прочие файлы `resources/regions/`, использованные при bake (уже в теге), и аргументы запуска.
4. **Среда**: точная сборка Godot (4.7.2 standard или .NET, хеш бинарника), .NET SDK, ОС, число потоков, включено ли C#-ядро (`terrain_kernel` в манифесте), размер архива.
5. **Как открыть**: команда запуска тега с подложенным кэшем. Ключ совпадёт только на той же сборке и при неизменённом `project.godot` — это ещё одна причина хранить продукты, а не надеяться на пересчёт.

Код V1 в master удаляется после принятия сети GEN2-5; тесты V1 удаляются вместе с ним по отдельному явному списку на утверждение. Ничего не ослабляется молча.
